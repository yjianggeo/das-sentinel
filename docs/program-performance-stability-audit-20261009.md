## 列表查询：已测量的主要瓶颈

从当前 `WindowService.list` 捕获真实 SQL，不调用完整列表服务。在已有 C 盘 SSD 诊断副本上，以 SQLite 3.53.3、只读连接和 `query_only` 执行 COUNT 与 30 条分页查询。副本约 4.90 GB，早于当前生产状态；每条查询设置 10 秒执行预算，全部完成。

| 查询（井下广覆盖排序） | 时间 | 进程逻辑读取量 | 结果 |
| --- | ---: | ---: | --- |
| 模型推荐、待复核 COUNT | 6.665 秒 | 385.35 MB | 返回一行总数 |
| 模型推荐、待复核第一页 | 0.505 秒 | 399.06 MB | 30 条记录 |
| 全部窗口 COUNT | 0.007 秒 | 2.94 MB | 返回一行总数 |
| 全部窗口第一页 | 6.634 秒 | 708.28 MB | 30 条记录 |

MB 按十进制计算。逻辑读取量包含操作系统缓存命中，不等于物理磁盘读取量；查询依次运行，缓存冷热不同，不能直接比较两个分页查询的速度。该测量不包含响应组装、源文件元数据校验、NAS 读取或图片加载，不能当作线上完整请求耗时。

证据与原因：

1. 全部窗口 COUNT 已在附加覆盖缓存连接之前构建，并走 analysis 覆盖主键索引。这个已有修复有效，必须保留。
2. 模型推荐 COUNT/PAGE 需要访问 analysis 的状态、输入 SHA、处理配置，以及最新匹配模型回执。当前索引不能覆盖这些读取；analysis 的部分字段位于大 `plan_json` 之后，存在大量溢出页访问。
3. 全部窗口分页仍按 `json_extract(result_json, '$.score')` 作为后续排序条件，需要读取大结果 JSON，再临时排序。仅调整 COUNT 不会解决这一成本。
4. 当前模型回执按 `window_id` 查找，未发现此前按 `status` 大范围扫描的坏计划重现。不能把再执行 ANALYZE 当作通用修复。

拟优先验证 analysis 小字段与 JSON 分数表达式的覆盖索引，以及最新回执/复核的复合索引，减少回表和临时排序。SQLite 官方说明覆盖索引可减少回表访问；是否被本项目查询采用、实际收益多大，仍须实测。[查询规划](https://www.sqlite.org/queryplanner.html)、[执行计划说明](https://www.sqlite.org/eqp.html)。

先在诊断副本验证筛选集合、总数、分页顺序和读取量。若索引不足以改善 JSON 排序，再单独设计轻量列表字段；本轮不直接引入第二套结果存储。生产建索引可能持有写锁，须先测量耗时并确定安全维护步骤，不能在扫描期间直接运行大表 DDL。

可复现基线：`D:/das-sentinel-runtime/manual-work/program-optimization-audit-20261009/list_readonly_baseline.py`、同目录 `list-readonly-baseline.json`。其中 COUNT 的 `rows: 1` 是返回行数，并非窗口总数。

首轮建议完成上表“首轮”中的小范围修改，并离线验证数据库候选。对每个改动先复现或写失败测试，再实施，最后比较改动前后。页面以请求次数、切图等待和标签保存反馈验收；数组及训练准备以数据和分组一致性验收；列表以同一快照的总数、顺序、逻辑读取量及重复计时验收。

API/前端可在验证通过后按现有方式上线。涉及数据库写锁、扫描 worker 重启的上线步骤必须先形成可审查的维护方案；本轮审查不执行这两项操作。新的模型质量实验、低频流程调整、全盘数据清理和算法更换不属于首轮性能修复。

本报告提出可验证的改动，没有承诺固定提速倍数。修改后的测试、性能对照和上线边界记录在首轮实施记录中。
